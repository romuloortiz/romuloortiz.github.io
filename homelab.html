01

Read this part first: none of this was me alone

Quick disclosure up front, because burying it in a closing section would undersell the actual point of this page: I don't have a systems administrator's background. Every stage that follows — the hardware call, the Docker Compose files, the security posture, the 3am cron job, the debugging stories you're about to read — happened because I directed Claude: set the goal, made the calls on tradeoffs, and reviewed the result, while Claude handled the parts that needed hands-on Linux depth, explained its reasoning when I asked, and remembered what it learned so the next problem didn't start from zero.

This isn't a "Claude helped a little" story. Claude is the operating system this whole project actually runs on top of — Ubuntu just boots the box. And it happened fast: this entire build, top to bottom, came together in a couple of weeks, not months — which is itself kind of the point. What follows is a real build log, with real hardware, real costs, real bugs, and real fixes; the difference from a normal one is that every decision point below was a conversation, not a manual I already had memorized.

What "directing Claude" actually looked like

Not prompt-once-and-pray. A running collaboration: describe the goal ("I want backups I can actually trust," "I want to know if a container dies at 2am"), let Claude propose an approach and explain the tradeoff when something sounded off, then let it write and run the actual commands — Docker Compose files, cron jobs, occ invocations, all of it. When things broke (and they broke — see the callouts throughout this page), Claude diagnosed it, fixed it, and turned the fix into something reusable instead of a one-time patch. That last part is the piece that compounds, and it's the part a search engine never does for you.

02

The machine

Nothing exotic, and not a fresh purchase either — the core of this box is a mini PC that's been running since 2020, given a second job instead of a trip to e-waste. Claude was the one who talked me out of buying anything new for the compute layer at all, once it walked through the actual case for reusing a 2020 desktop over a Raspberry Pi or a fresh NUC: the value of a home lab is uptime, not horsepower, and this six-year-old hardware still has plenty of the former left in it — bragging rights about teraflops can wait for a machine that isn't older than some of the subscriptions it just replaced.

Second life, not a purpose-bought server

The mini PC and its SSD go back to 2020, bought as an everyday Windows 10 desktop — nothing to do with this project at the time. When its CPU generation turned out to fall just short of Windows 11's hardware requirements, it was headed for e-waste for a licensing reason, not a broken one: nothing about the machine had actually failed. Wiped, put on Ubuntu, and repointed at a job it's genuinely well-suited for — sitting in a closet running lightweight services 24/7 — it got years of useful life back instead of a landfill, with Claude walking through the actual install and LUKS disk-encryption setup step by step — exactly the kind of one-shot, don't-get-it-wrong task where having someone who's done it a thousand times beats winging it from a wiki page. Everything else in the build below (RAM, the RAID enclosure, the data drive) was bought new, specifically for this.

03

Ubuntu, and why it's boring on purpose

Running Ubuntu 26.04.1 LTS ("Resolute Raccoon") — Claude's actual recommendation the moment it was asked "which distro for a box I'm not going to touch for years," and the reasoning held up: a five-year support window means this box can sit unattended for years without an OS-level end-of-life forcing a rebuild, which matters a lot more on a machine nobody looks at daily than it does on a laptop.

The other reason is unglamorous but real: when something breaks at 11pm, Ubuntu has the largest pile of Stack Overflow answers of any Linux distro. In practice, though, "ask Claude" beat "search Stack Overflow" every single time it actually came up — the pile of answers matters a lot less when the thing reading them for you already has, and can tell you which of them are outdated. For a one-person ops team, that's worth more than any technical edge a more "correct" distro might offer. Arch users, look away now.

04

Networking: Tailscale instead of port-forwarding

The box joined a personal Tailscale network — a mesh VPN built on WireGuard. Every device that needs to reach the server (laptop, phone, tablet) gets its own private key and its own 100.x.x.x address on the tailnet; the devices talk to each other directly over an encrypted tunnel, brokered by Tailscale's coordination servers but never routed through them. This wasn't a decision made by reading a security blog post — it came out of asking Claude to actually walk through the risk of forwarding a port at all, and "zero inbound ports, ever" was the answer that won.

Security consideration

Zero inbound ports are opened on the home router. There is nothing for a port scanner to find, because there is nothing listening on the public internet at all — every service (SSH, Nextcloud, the dashboards) is reachable only from devices already authenticated into the tailnet. Somewhere out there a bot is dutifully knocking on every port of this IP address and getting nothing but silence for its trouble. That's a meaningfully smaller attack surface than the traditional homelab approach of forwarding ports through the router and locking things down with a firewall and fail2ban after the fact — this way there's simply no door to pick the lock on.

It also scales for free: Tailscale's Personal plan covers the account holder plus 5 more people (6 total) with no cap on devices per person. Right now the tailnet already has 3 logins and 8 devices on it — laptops, phones, a tablet — at zero cost, which still leaves headroom, but not infinite headroom: every new invite is a deliberate call against that ceiling, not a default yes.

05

Remote access via SSH, then installing the actual administrator

With the tailnet in place, openssh-server went on next — this is what actually lets the box get administered from anywhere, instead of requiring a keyboard plugged into it. The daemon itself binds normally; what makes it safe is that nothing upstream ever forwards a connection to it from the open internet, so in practice it's reachable only over the tailnet's private address space, from devices that are already trusted. Confirming that the default config didn't need anything hardened beyond what the tailnet already provides took a few minutes of back-and-forth with Claude, not an afternoon of second-guessing a hardening guide.

The very next thing installed, over that same SSH session, was Claude Code — the tool that ends up doing basically everything described on this page from this point forward. This is the moment "remote access" stopped meaning "a terminal I can reach from anywhere" and started meaning "an admin I can reach from anywhere."

Gemini CLI, installed alongside as a designated understudy

Gemini CLI went on at the same time, not because the setup needed two assistants, but as a deliberate plan for after the setup was done: once the initial build settled, day-to-day maintenance (nightly-check triage, routine updates, the occasional "why did this alert fire") is light enough work to hand to a free tier, keeping Claude for anything that actually needs it.

Why the free tier is actually enough for this, model by model

The catch is that "Gemini's free tier" isn't one thing — it's split sharply by model, and that split is what makes this work at all. Gemini Flash-Lite's free tier runs in the neighborhood of 15 requests per minute and roughly 1,000 requests per day, with a generous shared token-per-minute ceiling behind it. The plain Flash model, by contrast, has had its free daily allowance cut hard over time — user reports on Google's own developer forum describe it dropping as low as ~20 requests a day in recent rate-limit changes, which is nowhere near enough for anything beyond kicking the tires. That's the entire reason this only works in Flash-Lite mode specifically, not "Gemini" generically — the full model's free tier isn't built for sustained use, and Google doesn't publish these numbers as a fixed table anyway (its own docs point you at AI Studio's live dashboard for your actual current limits, because they get adjusted). For a homelab specifically, the math holds up well even on the conservative end: routine admin work here is bursty and occasional — a nightly notification triaged, an update runbook run every so often, an alert investigated — not a continuous stream of requests, so ~1,000/day of headroom on Flash-Lite comfortably covers real usage with plenty to spare, right up until something big enough happens that it's worth switching back to Claude for the afternoon.

06

Nextcloud: the subscription killer

Nextcloud runs in Docker, with its file storage pointed straight at the RAID1 mount — so every photo and document rides on mirrored disks from day one, not as an afterthought. Three accounts are set up: both parents and a 14-year-old son. Two of the three have actually moved their data in so far; the third has an account waiting and no particular urgency to fill it — migrating "in the fullness of time" is a perfectly acceptable pace for a project nobody's charging late fees on, unlike certain other subscription services that shall remain named in the next sentence.

Photo libraries have been migrated in from iCloud, Google Photos, and — as of the last one to fall — Dropbox, each one moved over by an extract/process/filter/upload pipeline Claude wrote and ran, not a manual drag-and-drop through three different web UIs. One self-hosted app has now fully replaced three separate subscriptions — Google One (the one plan covering both Google Photos and Google Drive — they're not two subscriptions, just two faces of the same one), iCloud storage, and Dropbox — for the cost of the electricity to run the box.

What this actually gets you

Nextcloud on its own is the file-storage layer — a self-hosted Dropbox: folders, sync, sharing, access from any device. What turns that into an actual iCloud/Google Photos replacement is two apps riding on top of it. Memories is the photo experience: a timeline you scroll by date, map view by location, and — because Recognize runs the ML side of it — automatic face grouping and object/scene tagging, the same conveniences the big-tech photo apps use to sell you on staying put. Groupware (calendar, contacts, mail) is the other half: point your phone's native calendar and contacts apps at it over the same open standards (CalDAV/CardDAV) any client already speaks, and Google Calendar or iCloud Calendar quietly stop being load-bearing. None of this needs a browser day-to-day — Nextcloud's own iOS app handles it, including camera-roll auto-upload, so photos land on your own server the moment they're taken, the same way iCloud Photos or Google Photos would do it automatically in the background.

The "cost of electricity" line, quantified

Because a build log that just asserts "electricity is basically free" and moves on isn't actually a build log — it's a vibe. Working estimate at $0.12/kWh: roughly 35-40W continuous draw, and the two spinning 7200RPM drives in the RAID enclosure are the real power hog here (~18W of it), not the low-power laptop chip actually doing the computing (~15-20W). That works out to about $3-4 a month — call it $40/year to retire three subscriptions that would've cost that much in a single week. Still waiting on an actual Kill-A-Watt reading to replace "estimate" with "measured," but the receipts-obsessed instinct of this whole page demanded a number instead of a shrug.

07

Firefly III: the Quicken killer

The newest addition, and the reason the subscription count in the header didn't stop at three: Firefly III, a self-hosted, double-entry personal finance manager, replacing a Quicken subscription the same way Nextcloud replaced the cloud-storage stack — one self-hosted app, zero recurring cost, and one fewer company that gets to email me about a price increase.

Three containers, same shape as Nextcloud plus one extra
appThe web app itself — same db+app split Nextcloud uses
dbMariaDB, pinned to the same tag Nextcloud's DB already uses, so only one image tag needs tracking instead of two
cronA tiny container whose only job is pinging Firefly's own cron endpoint once a day, for recurring transactions and scheduled rules — Nextcloud doesn't need this piece, Firefly ships it as part of its own recommended setup

Uploaded attachments and the database both live on the RAID mount, not a Docker-managed volume — the same "data lives where it can actually be backed up" rule Nextcloud follows — which is also why Firefly slotted straight into the existing nightly backup run (see Backup strategy, next) instead of needing a system of its own.

Environment quirk — sudo has no terminal here

Creating the RAID-side data directories needed sudo, and it turned out neither an automated command nor even the human typing it directly into the same terminal session could get sudo a real controlling TTY to authenticate against — a hard limitation of this particular setup, not a permissions mistake. The kind of environment-specific gotcha that would've eaten an evening of guessing on my own; Claude narrowed it down to "this session has no TTY" in a couple of exchanges. The fix was mundane once identified: open a genuinely separate terminal, outside that session entirely, and run it there. Worth remembering before assuming any future sudo step will just work the same way everything else here does.

A health check that actually checks something

Firefly ships a dedicated GET /health route that runs a real database query (not just "is the process alive") and returns plain-text OK. Plain text, notably — not JSON like the other services' health checks, which matters for wiring it into Uptime Kuma: it needs an HTTP(s) - Keyword monitor (keyword OK), not a JSON Query monitor, or the check would fail to parse a response that was never JSON in the first place. Docker Container monitors cover all three containers the same way Nextcloud's two do.

First boot took several minutes longer than Nextcloud's did — not a hang, just Firefly running its entire historical migration-and-upgrade chain in sequence on what was, seconds earlier, an empty database. Steady progress in the logs, not silence, is what that looks like from the outside — worth checking before assuming a slow first boot means a broken one.

What this actually gets you

Firefly III is a real double-entry personal finance manager — the Quicken/YNAB category: every checking, savings, and credit card account in one place, budgets that actually reconcile against real transactions, and a genuine picture of net worth over time, not just a balance number per app. The bigger difference from a cloud finance app is what it doesn't ask for: no bank-login aggregator service sitting between your accounts and the dashboard, no third party whose business model depends on categorizing your spending. Firefly itself has no official mobile app, which sounds like a gap until you notice it's a fully open API instead — Abacus, a well-regarded third-party iOS client, is what actually sits on the phone here, and it's a properly native experience: add a transaction between calls, check a balance at checkout, without ever opening a browser. Self-hosted backend, best-of-breed client, no single company owning both ends.

08

Alerting: three containers, three different questions

A server nobody's watching is a server that fails silently, usually at the worst possible moment, usually right when you're bragging about it to someone. The three-tool split below wasn't a design I brought to Claude — it's the shape it proposed after being asked "how do I actually know if any of this breaks," and it's held up ever since. Three small containers each answer a different question, and all of them funnel into the same place:

Monitoring containers
BeszelIs the hardware healthy? — CPU, RAM, disk, temperature, per‑container stats
Uptime KumaAre the apps actually working? — 6 container checks, 3 real HTTP health‑check queries, 1 outbound ping to tell "server's down" apart from "internet's down"
ntfyThe delivery pipe — the one channel every alert, from either tool (or a cron job), gets pushed through
Beszel＋Uptime Kuma＋cron →ntfy (self‑hosted) → over Tailscale →iPhone

ntfy itself is self-hosted with no public address, so the phone subscribes to it over the tailnet's private hostname. The one subtlety: getting real background push on iOS required routing through the public ntfy.sh purely as a relay to wake Apple's push service — a self-hosted server has no way to talk to APNs directly, so ntfy.sh does that one hop on its behalf while every actual message still originates and stays on the home server. This is the kind of platform-specific wrinkle that would've cost real research time to even know existed; Claude flagged it before the push notifications ever failed to arrive, not after.

Cron-driven, on purpose split two ways

An 8am job bundles six separate staleness checks — OS packages and a pending-reboot flag, plus four more added later (see Staying current, below) — and stays silent if there's nothing to report, so a clear box doesn't turn into a daily "all good!" ping nobody reads. A 3am backup job does the opposite: it sends exactly one notification every single morning, success or failure, because for a backup, silence is ambiguous rather than reassuring — you want to know it ran, not just assume it did.

What this actually gets you

None of this lives behind a browser tab you have to remember to open. Beszel and Uptime Kuma both have real iOS apps, so hardware health and uptime status are a home-screen icon away, not a bookmarked URL; ntfy's app is what actually turns its push notifications into the kind that lock-screen the phone, not an email that sits unread. The end result is a genuinely native "is my stuff okay" experience running entirely on hardware in a closet, with none of it costing a subscription or handing status data to a third party to find out.

Backup strategy

Nightly at 3am, a script Claude wrote, tested, and then explained back line by line — until "trust me it works" turned into "I actually understand why it works" — covers every stateful service on the box, not just the two apps with irreplaceable user data: Nextcloud's files and database, Firefly III's uploaded attachments and database, and the entire monitoring stack's configuration — ntfy's subscriptions, Beszel's dashboard config, Uptime Kuma's monitor history — each kept separate on purpose, to the dedicated 1TB drive using restic:

Nightly backup sequence
1mysqldump the Nextcloud database to a fixed filename
2restic backup the Nextcloud data on the RAID (tagged separately)
3restic backup the Nextcloud database dump (tagged separately)
4mysqldump the Firefly III database to a fixed filename
5restic backup Firefly's uploaded attachments on the RAID (tagged separately)
6restic backup the Firefly database dump (tagged separately)
7restic backup ntfy's subscription/topic state (tagged separately)
8restic backup Beszel's dashboard config and history (tagged separately, excluding the agent's own SSH private key — see below)
9restic backup Uptime Kuma's monitor config and history (tagged separately)
10restic forget --prune — keep 7 daily / 4 weekly / 6 monthly, across all seven categories
11One ntfy notification with all seven sizes, success or fail

Splitting each source into its own restic call means the morning notification can report a size for each independently — useful for noticing, at a glance, if a database dump quietly went to zero bytes while its file backup looked fine. Restic deduplicates block-level, so even though the notification always shows the full current size of each source, the actual bytes written to the backup drive each night are just what changed. One script, one schedule, one consolidated notification — every new service (Firefly, then later the monitoring stack) meant extending the existing run rather than standing up a parallel backup system for it, which is exactly the instinct that keeps "one script that covers everything" from quietly turning into "five scripts, three of which nobody remembers to check."

One deliberate exclusion, not an oversight

Beszel's data directory holds one file the backup user can't read: the beszel-agent's own SSH private key, root-owned at mode 600. Backing it up wasn't worth loosening its permissions for — losing it just means the agent container re-provisions a new one on next start, not real data loss — so it's explicitly excluded rather than silently failing the whole backup over one unreadable file restic would otherwise choke on.

This replaced a setup that was, honestly, just RAID1 — which only protects against a single disk dying, not against a fat-fingered delete or a ransomware scenario, both of which this restic setup now actually covers via retained snapshots. "I have RAID1" is not a backup strategy, it's a very expensive way to still lose everything with extra steps and a false sense of security — a distinction Claude drew early and that reshaped the whole approach. A true offsite third copy — pushed to a remote machine over Tailscale, for a textbook 3‑2‑1 — was considered and deliberately shelved rather than left as an oversight: the remaining gap is a scenario like a house fire taking out the RAID and the backup drive together, and at that point the missing hard drive is not going to be the priority. Local RAID1 plus a dedicated backup drive is judged sufficient for the actual cost-vs-risk tradeoff here.

Staying current: six update systems, one push

A server that's up doesn't mean a server that's current — it just means it's up, quietly getting older and more vulnerable while looking perfectly fine from the outside. OS packages, two hand-installed CLI tools, eight Docker images, and Nextcloud's own app store all drift out of date on six completely independent clocks. Consolidating six unrelated update stories into one daily push was Claude's idea, not a design I brought to it — the ask was simply "tell me if anything on this box needs attention," and what came back was an actual system, not just a cron job.

What the 8am job checks
OS packagesapt list --upgradable — names each package and its version transition, not just a count
Pending reboot/var/run/reboot-required present
CLI toolnpm outdated -g for gemini-cli — not apt-managed, needs its own check
Claude Code itselfinstalled version vs. npm view @anthropic-ai/claude-code version — Anthropic's native installer isn't apt- or npm-managed either, but the npm registry's published version tracks it 1:1; the tool that runs this whole homelab checks its own freshness alongside everything else it maintains
8 container imageslocal vs. registry digest — catches a rebuilt :latest even when the tag string never changes; now covers Firefly III's app + DB too
Nextcloud appsocc update:check inside the container — apps version through the app store, not the image
Why a :latest tag lies

A tag like :latest is a pointer, not a version number — the maintainer can rebuild and repoint it any day without the string changing at all. Comparing tags would miss that entirely, so the check instead diffs each image's actual content digest, before and after an authoritative docker pull, against what's running locally. Different digest, same tag, still an update.

Debugging story — when the check itself was lying

First real run flagged all 6 watched images as outdated. Applying them one by one told a different story: only 2 actually were. The original check peeked at the registry digest via docker manifest inspect, specifically to avoid downloading anything just to check — but that endpoint served a stale digest for 4 of the 6 images, a known caching quirk on Docker Hub's manifest-list responses that a plain content pull doesn't hit, since it resolves through a different, authoritative path. Claude traced the discrepancy back to that exact caching quirk rather than just shrugging and re-running the check. A monitoring check that cries wolf is worse than no check at all — a few missed alerts erode trust faster than the alerts themselves are worth — so the fix was to stop peeking and just pull for real, diffing the digest before and after. It costs a little bandwidth on nights something's actually new; every other night it's already a no-op, since the layers are already local.

One image doesn't fit either pattern cleanly: the Nextcloud app container. Watching that story unfold is why a plain docker pull was never going to be enough for it.

Debugging story — the HEIC rabbit hole

1,553 HEIC photos from a fresh iCloud import never appeared in the photo-timeline app's feed, with zero errors anywhere. Root cause: Nextcloud only enables a narrow default set of preview handlers, and the two that matter here — HEIC images and video thumbnails — aren't in it. The timeline app checks a file's format against that same enabled list before it will even index it, so every HEIC silently got skipped before its metadata was ever read. Claude traced it by planting temporary log lines inside the app's own indexing code, because every layer looked fine in isolation — the image library decoded HEIC standalone without issue, it was only the combination that failed. That's real debugging, not a lucky guess: forming a hypothesis, instrumenting the actual code to test it, and reading the result. The config fix was one line; video thumbnails needed something the base Nextcloud image doesn't ship at all: an actual ffmpeg binary. Installing it by hand worked until the next container restart wiped it out — so it got baked into a small custom image instead, layered on top of the official one, that survives recreation.

Detection and remediation still stay deliberately separate, just with one nuance: the check itself now pulls new layers when it finds a real update (that's what the fix above requires), but it never recreates a running container on its own. Each watched system gets its own one-shot runbook for that half — Claude-authored, invoked by hand, never triggered automatically, and each one verifies itself before calling the job done rather than just trusting the pull succeeded:

  2. docker compose pull db.
  3. docker compose up -d db — recreate (the data dir lives on the RAID, untouched by the swap).

Physical maintenance: shutting the box down safely

Every update runbook above assumes the machine stays powered on. A RAM upgrade doesn't — at some point you have to actually crack the case open, which means the box has to come down for real, and "unplug it and hope" is not a runbook. That's a different problem: nine containers across three stacks, a RAID enclosure and a backup drive that both need to come back mounted, and a nightly backup job that isn't even a container. Two runbooks now bracket that process — authored by Claude in the same "one-shot, human-invoked, self-verifying" shape as the update skills, precisely because a real power-down was the one operation on this whole box where getting the order of steps wrong could actually lose data:

/pre-shutdown-sequencebefore the power comes off▸
  1. Check for a live backup — the nightly restic run is a host cron job, not a container, so docker ps and docker compose down are both blind to it. Shutting down mid-backup is a real way to get a half-written repo.
  2. Confirm both external mounts (RAID data volume, USB backup drive) are actually present before touching anything.
  3. Pause the 7 Uptime Kuma monitors watching Nextcloud and Firefly — they'd otherwise sit in a "pending" state while those containers stop, with a real (if narrow) chance of escalating into a false alert (see callout below).
  4. docker compose down all three stacks — Nextcloud, Firefly III, monitoring — in that order.
  5. Confirm nothing's left in docker ps, then hand off: the actual sudo shutdown has to be run by hand in its own terminal, since sudo has no controlling TTY through an automated session here (same quirk noted under Firefly III, above).
/post-restart-sequenceafter the power comes back▸
  1. Check both external mounts remounted before starting any container — starting Nextcloud against an empty mountpoint would look like a clean boot while quietly serving no data.
  2. docker compose up -d all three stacks — they were downed, not just stopped, so nothing restarts on its own.
  3. Health-check each service the same way the update runbooks do: occ status, the Firefly /health endpoint, container status for the rest.
  4. Resume the same 7 Kuma monitors once Nextcloud and Firefly are confirmed healthy — they stay paused across the reboot otherwise, since Kuma's data survives on a bind mount.
  5. After a RAM upgrade specifically, free -h to confirm the new total actually shows up.
Why the mounts don't care about USB re-enumeration

Both the RAID enclosure and the backup drive are mounted by filesystem UUID in /etc/fstab, not by device letter — so it doesn't matter if the kernel hands the RAID enclosure /dev/sdb instead of /dev/sda after a reboot, which USB devices do fairly often depending on enumeration order at boot. Both also carry nofail, so a drive that didn't reconnect cleanly won't hang the boot — which cuts both ways: it also means a missing mount won't announce itself as an error, so the post-restart check has to look for it explicitly rather than trusting a clean boot.

Debugging story — pgrep catching its own tail

The pre-shutdown check for a live backup process first ran as pgrep -fa restic, which matched every single time — including with no backup running. -f matches the full command line, and the check's own invocation was a shell one-liner that contained the word "restic" in its own text, so the process was matching itself. Claude caught the self-match and switched the check to pgrep -x restic, which matches only the exact process name, not the full command line an unrelated process happens to mention.

Debugging story — the monitor that watched its own shutdown, then couldn't tell anyone

Expected Uptime Kuma to light up the phone during the first real shutdown; it didn't, just a few yellow squares. Turned out every monitor needs 5 consecutive failed checks a minute apart — about 5 minutes — before Kuma calls something actually down and fires a notification. The Nextcloud and Firefly containers each failed exactly once before Kuma's own container went down seconds later as part of the same monitoring stack shutdown, so nothing ever crossed the threshold. A monitor can't escalate an alert about an outage it's no longer running to witness. Beszel turned out to have real alert rules too (a correction to what this page used to say about it, caught by double-checking rather than assuming the earlier writeup was still accurate), with an even longer 10-minute grace period on host-down — but nothing it watches goes down before its own hub does, so it was never at risk the way Kuma was. Fix: both runbooks above now explicitly pause and resume just the 7 monitors that watch services stopped individually, ahead of the stack that watches them.
