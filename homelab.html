01

The machine

Nothing exotic, and not a fresh purchase either — the core of this box is a mini PC that's been running since 2020, given a second job instead of a trip to e-waste. It runs 24/7 in a closet, which is really the whole trick: the value of a home lab is uptime, not horsepower, and this hardware still has plenty of the former left in it.

Second life, not a purpose-bought server

The mini PC and its SSD go back to 2020, bought as an everyday Windows 10 desktop — nothing to do with this project at the time. When its CPU generation turned out to fall just short of Windows 11's hardware requirements, it was headed for e-waste for a licensing reason, not a broken one: nothing about the machine had actually failed. Wiped, put on Ubuntu, and repointed at a job it's genuinely well-suited for — sitting in a closet running lightweight services 24/7 — it got years of useful life back instead of a landfill. Everything else in the build below (RAM, the RAID enclosure, the data drive) was bought new, specifically for this.

Three separate drives, three separate jobs: the OS lives on its own encrypted disk so a stolen or discarded drive doesn't leak anything; the RAID1 volume holds the data that actually matters and survives a single-disk failure; the USB drive never holds anything except backups, so a bad rm -rf on the main box can't take the backup with it.

02

Ubuntu, and why it's boring on purpose

Running Ubuntu 26.04.1 LTS ("Resolute Raccoon"). LTS specifically — a five-year support window means this box can sit unattended for years without an OS-level end-of-life forcing a rebuild, which matters a lot more on a machine nobody looks at daily than it does on a laptop.

The other reason is unglamorous but real: when something breaks at 11pm, Ubuntu has the largest pile of Stack Overflow answers of any Linux distro. For a one-person ops team, that's worth more than any technical edge a more "correct" distro might offer.

03

Networking: Tailscale instead of port-forwarding

The box joined a personal Tailscale network — a mesh VPN built on WireGuard. Every device that needs to reach the server (laptop, phone, tablet) gets its own private key and its own 100.x.x.x address on the tailnet; the devices talk to each other directly over an encrypted tunnel, brokered by Tailscale's coordination servers but never routed through them.

Security consideration

Zero inbound ports are opened on the home router. There is nothing for a port scanner to find, because there is nothing listening on the public internet at all — every service (SSH, Nextcloud, the dashboards) is reachable only from devices already authenticated into the tailnet. That's a meaningfully smaller attack surface than the traditional homelab approach of forwarding ports through the router and locking things down with a firewall and fail2ban after the fact.

It also scales for free: the personal plan covers up to 5 people with no cap on devices per person. Right now the tailnet already has 3 logins and 8 devices on it — laptops, phones, a tablet — at zero cost.

04

Remote access via SSH

With the tailnet in place, openssh-server went on next — this is what actually lets the box get administered from anywhere, instead of requiring a keyboard plugged into it. The daemon itself binds normally; what makes it safe is that nothing upstream ever forwards a connection to it from the open internet, so in practice it's reachable only over the tailnet's private address space, from devices that are already trusted.

05

Nextcloud: the subscription killer

Nextcloud runs in Docker, with its file storage pointed straight at the RAID1 mount — so every photo and document rides on mirrored disks from day one, not as an afterthought. Three accounts are set up: the two parents and a 14-year-old son.

Photo libraries have already been migrated in from iCloud and Google Photos; a Dropbox migration is next in the queue. Once that's done, one self-hosted app will have fully replaced four separate paid or freemium services — Google Photos, Google Drive, iCloud storage, and Dropbox — for the cost of the electricity to run the box.

06

Alerting: three containers, three different questions

A server nobody's watching is a server that fails silently. Three small containers each answer a different question, and all of them funnel into the same place:

Monitoring containers
BeszelIs the hardware healthy? — CPU, RAM, disk, temperature, per‑container stats
Uptime KumaAre the apps actually working? — 6 container checks, 3 real HTTP health‑check queries, 1 outbound ping to tell "server's down" apart from "internet's down"
ntfyThe delivery pipe — the one channel every alert, from either tool (or a cron job), gets pushed through
Beszel＋Uptime Kuma＋cron →ntfy (self‑hosted) → over Tailscale →iPhone

ntfy itself is self-hosted with no public address, so the phone subscribes to it over the tailnet's private hostname. The one subtlety: getting real background push on iOS required routing through the public ntfy.sh purely as a relay to wake Apple's push service — a self-hosted server has no way to talk to APNs directly, so ntfy.sh does that one hop on its behalf while every actual message still originates and stays on the home server.

Cron-driven, on purpose split two ways

An 8am job bundles six separate staleness checks — OS packages and a pending-reboot flag, plus four more added later (next section) — and stays silent if there's nothing to report, so a clear box doesn't turn into a daily "all good!" ping nobody reads. A 3am backup job does the opposite: it sends exactly one notification every single morning, success or failure, because for a backup, silence is ambiguous rather than reassuring — you want to know it ran, not just assume it did.

07

Backup strategy

Nightly at 3am, a script backs up both the Nextcloud files and the database — separately, on purpose — to the dedicated 250GB drive using restic:

Nightly backup sequence
1mysqldump the full database to a fixed filename
2restic backup the Nextcloud data on the RAID (tagged separately)
3restic backup the database dump (tagged separately)
4restic forget --prune — keep 7 daily / 4 weekly / 6 monthly
5One ntfy notification with both sizes, success or fail

Splitting data and database into two restic calls means the morning notification can report a size for each independently — useful for noticing, at a glance, if the database dump quietly went to zero bytes while the file backup looked fine. Restic deduplicates block-level, so even though the notification always shows the full current size of each source, the actual bytes written to the backup drive each night are just what changed.

This replaced a setup that was, honestly, just RAID1 — which only protects against a single disk dying, not against a fat-fingered delete, a ransomware scenario, or the whole enclosure failing at once. The one gap left is offsite: a second copy pushed to a remote machine over the same Tailscale network, for a proper 3‑2‑1, isn't built yet.

08

Staying current: six update systems, one push

A server that's up doesn't mean a server that's current. OS packages, two hand-installed CLI tools, six Docker images, and Nextcloud's own app store all drift out of date on six completely independent clocks — so the 8am job was widened until none of them could go stale unnoticed.

What the 8am job checks
OS packagesapt list --upgradable — names each package and its version transition, not just a count
Pending reboot/var/run/reboot-required present
CLI toolnpm outdated -g for gemini-cli — not apt-managed, needs its own check
Claude Code itselfinstalled version vs. npm view @anthropic-ai/claude-code version — Anthropic's native installer isn't apt- or npm-managed either, but the npm registry's published version tracks it 1:1
6 container imageslocal vs. registry digest — catches a rebuilt :latest even when the tag string never changes
Nextcloud appsocc update:check inside the container — apps version through the app store, not the image
Why a :latest tag lies

A tag like :latest is a pointer, not a version number — the maintainer can rebuild and repoint it any day without the string changing at all. Comparing tags would miss that entirely, so the check instead diffs each image's actual content digest, before and after an authoritative docker pull, against what's running locally. Different digest, same tag, still an update.

Debugging story — when the check itself was lying

First real run flagged all 6 watched images as outdated. Applying them one by one told a different story: only 2 actually were. The original check peeked at the registry digest via docker manifest inspect, specifically to avoid downloading anything just to check — but that endpoint served a stale digest for 4 of the 6 images, a known caching quirk on Docker Hub's manifest-list responses that a plain content pull doesn't hit, since it resolves through a different, authoritative path. A monitoring check that cries wolf is worse than no check at all — a few missed alerts erode trust faster than the alerts themselves are worth — so the fix was to stop peeking and just pull for real, diffing the digest before and after. It costs a little bandwidth on nights something's actually new; every other night it's already a no-op, since the layers are already local.

One image doesn't fit either pattern cleanly: the Nextcloud app container. Watching that story unfold is why a plain docker pull was never going to be enough for it.

Debugging story — the HEIC rabbit hole

1,553 HEIC photos from a fresh iCloud import never appeared in the photo-timeline app's feed, with zero errors anywhere. Root cause: Nextcloud only enables a narrow default set of preview handlers, and the two that matter here — HEIC images and video thumbnails — aren't in it. The timeline app checks a file's format against that same enabled list before it will even index it, so every HEIC silently got skipped before its metadata was ever read. Tracing it took planting temporary log lines inside the app's own indexing code, because every layer looked fine in isolation — the image library decoded HEIC standalone without issue, it was only the combination that failed. The config fix was one line; video thumbnails needed something the base Nextcloud image doesn't ship at all: an actual ffmpeg binary. Installing it by hand worked until the next container restart wiped it out — so it got baked into a small custom image instead, layered on top of the official one, that survives recreation.

Detection and remediation still stay deliberately separate, just with one nuance: the check itself now pulls new layers when it finds a real update (that's what the fix above requires), but it never recreates a running container on its own. Each watched system gets its own one-shot runbook for that half — invoked by hand, never triggered automatically, and each one verifies itself before calling the job done rather than just trusting the pull succeeded:

/update-ntfynotification hub▸
  1. docker compose pull ntfy — fetch the latest image.
  2. docker compose up -d ntfy — recreate the container (./ntfy-data is a bind mount, untouched by the swap).
  3. Confirm health: container shows "Up", and curl localhost:8081/v1/health returns {"healthy":true}.
  4. Send a live test push through the real topic, to confirm delivery still works end-to-end, not just that the process started.
  5. Report the before/after image digest.
/update-beszelhub + agent, together▸
  1. docker compose pull beszel beszel-agent — both images, in one step, on purpose: hub and agent are the same product, and letting one drift a version behind the other risks breaking their connection.
  2. docker compose up -d beszel beszel-agent — recreate both.
  3. Confirm both containers are "Up," then check the dashboard itself shows the agent still connected and reporting fresh metrics — not just stale numbers from before the restart.
  4. Report before/after digests for both images.
